# Contributing

Thank you for improving dash9. Discuss substantial behaviour in an issue and update or add a specification before implementation — `SPEC.md` for Phase 1 capabilities, a new file under `docs/specs/` for later phases. Record durable architecture decisions in an ADR under `docs/adr/`. Use conventional commits (`type(scope): summary`), such as `feat(prom): add label metadata queries`.

Fork the repository, create a focused branch, run `just ci`, and submit a pull request using the template. New dependencies need a documented role, license review, maintenance assessment, and minimal feature set — `dash9-core` in particular must never gain a UI, network, or async-runtime dependency (see `AGENTS.md`). License review is enforced mechanically, not just by eye: `just deny` (`cargo deny check`, also run in CI) fails on a license outside `deny.toml`'s allow-list, a banned/duplicate-version crate, an unapproved source, or a RUSTSEC advisory — adding a dependency under a new license means updating `deny.toml` in the same PR, with a reason. Defect fixes require a regression test. The command grammar and dashboard TOML schema are public, versioned formats: extending them means adding a new verb, subverb, or field, never changing an existing one's meaning (`SPEC.md` Section B.1).

Keep tests deterministic and offline. Prefer a fixture or a throwaway local TCP listener the test itself owns over a live network dependency — see `crates/dash9-prom/src/lib.rs`'s `live_tests` module and `crates/dash9/tests/cli.rs` for the established pattern.

## Debugging a live TUI report that doesn't match the code

When a bug report describes behavior that seems to contradict what the code review says should happen — common in the TUI, where the same key means different things depending on region/zoom/editing state (`docs/specs/open.md` Sections E-H) — don't just re-read the code a second time and guess harder. Add temporary instrumentation and drive it live.

The pattern that root-caused a real, repeated case of this (`crates/dash9-tui/src/status_bar.rs`, PRs #21/#22 in this repo's history): a one-line `DBG: region=... zoom=... editing=... focus=N/M log_scroll=... last_key=.../Press` segment appended to the status bar, wired through as its own separate, obviously-temporary parameter (`draw_status_bar`'s `debug: Option<&str>` arg at the time — never folded into `StatusBarModel` itself, so it couldn't be mistaken for a real field). Drive it with `tmux new-session -d -x <cols> -y <rows>`, `tmux send-keys -l "<literal>"` (use `-l` for literal text, plain key names like `PageDown` otherwise), and `tmux capture-pane -p` (`-e` if you need real ANSI colors, not just text) after each press — send the exact key sequence the report describes and watch whether the debug fields actually move the way the code claims they should.

This conclusively separates two very different bugs: "the key-handling mechanism is broken" vs. "the mechanism works exactly as coded, but the UI gives no visible signal for state that silently changes what a key does." Three separate-seeming reports here ("`PageDown` isn't working," "`Tab` is flipping panels," "arrows are captured by the command box") all turned out to be the second kind — `last_key` and `log_scroll` were confirmed moving in lockstep with every press, proving the mechanics were always correct; the real, repeated cause was that `editing` state was easy to enter (`Tab`-cycling into the command box, or a submitted command silently reopening an empty one) and easy to miss, since the only signal was a small `:` in the command box.

**Remove the instrumentation once it's done its job.** It answered the question it was added for; leaving it in — even behind a flag — is dead weight and a second place the same state can drift out of sync with the real one. The actual fix belongs in the UI, not a debug line: here, naming `editing` right in the zoom bar's bracket label (`"[Grid + editing]"`) instead of leaving it an easy-to-miss `:`.
